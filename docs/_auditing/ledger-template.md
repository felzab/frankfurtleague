# Ledger template

Copy this file to `docs/audit/0-remediation-ledger.md` when a programme's passes are complete, and
fill it in. The structure is extracted from the frontend programme's ledger (2026-07); the rules
baked into it are the fixes for every way that ledger broke — see
[`lessons.md §7`](lessons.md#7-ledger-discipline--how-it-broke-and-the-rules-that-fixed-it).

Angle-bracketed text is placeholder. Everything else is the standing rule and copies verbatim.

---

````markdown
# Remediation Ledger — <programme name>

**Purpose.** The single working document for remediating all findings from the <N> audit reports.
The reports are the evidence; this file is the plan and the state. A session reads this file and the
_specific report sections_ for the wave in progress — never a whole report, never two reports.

**Wave reports live in [`wave-reports.md`](wave-reports.md).** This file tracks _what must be done
and whether it is done_; that file records _what was actually done and why_. Keep the narrative
there and the status here.

**Source reports** (in `docs/audit/`, written in this order):

| Ref | File   | Findings | CRIT | HIGH | Character                        |
| --- | ------ | -------: | :--: | :--: | -------------------------------- |
| R1  | <file> |      <n> | <n>  | <n>  | <one-line character of the pass> |

---

## How to read this file

- **ID** — stable identifier, `R<report>-<section>`. Cite it in commit messages and PR titles.
  Findings discovered outside the reports get `NEW-<theme><n>`.
- **§** — the section to open in the source report. Always read it before editing; summaries here
  are lossy by design.
- **Files** — the primary file reference. A _starting point_, not the blast radius.
- **Status** — `[ ]` open · `[~]` in progress · `[x]` done · `[!]` blocked · `[-]` won't do.

**The ledger row wins wherever it contradicts the source report.** Wave 0 answers and later waves
amend findings; the reports are never updated to match.

**Severity is not priority.** Wave assignment already accounts for severity, blast radius, cost and
dependency order. Work the waves in order; do not re-sort by severity.

**Row hygiene.** A closed row is a status marker, the forward constraints a later wave must obey,
and a report link — 150–600 characters. `[-]` and `[!]` need the reason, the evidence, and a
**reversal trigger**. Never bulk-edit this file with pattern-matched scripts; use line-scoped edits
and diff against the latest `.snapshots/` copy before moving on.

# Part 4 — Verification gate

Run before every merge, in every wave, without exception:

```bash
./scripts/verify.sh          # full gate: pnpm verify + audit + backend ruff/pytest + both images + sanity
./scripts/verify.sh --quick  # skips the image builds
```
````

**Run the script, never a hand-typed chain** — a hand-typed chain is a chain someone drops a link
from. Any new check goes _inside_ the script, so no future session has to be told about it.
`--quick` is not sufficient for changes touching `src/core/config.ts`, `src/core/auth.ts`,
`src/instrumentation.ts`, or anything only a built image exercises. The gate mutates the tree
(prettier runs in write mode first) — commit what it reformats. Record the lint-warning baseline
here at Wave 1 so later waves can tell new violations from inherited ones.

# Part 4b — Wave report (required, every wave)

Before opening the wave's PR, write its section in `wave-reports.md` using the template there. A
wave is not finished until its report exists. Then trim the ledger rows — rows are status; the
report is the story.

**Wave reports are written for humans, not for machines.** The audience is someone who was not in
the session — the owner six months later, a reviewer, a future session. Rules that follow from
that: the "what this wave was for" paragraph must be readable by a non-engineer; changes are
grouped by theme and explained as defect → fix → visible effect in full sentences; row IDs appear
in passing for greppability, never as the load-bearing text — a reader must not need the ledger
open to follow the story; tables are for enumerable facts, prose for everything that needs
explaining; and failed attempts, reversals and unresolved anomalies are narrated honestly, because
a report that lists only successes tells the next reader nothing the diff does not.

**Lessons harvest (same step, same commit).** Any new misstep, false positive, library trap,
environment trap or process failure of value beyond this programme is **verified first**
(reproduced, or confirmed at the library source / running system) and then merged into the
matching theme of `docs/_auditing/lessons.md` — never appended as a per-wave dump. Programme-local
detail stays in the wave report; only the durable, transferable lesson moves.

# Part 4c — Consistency sweep (required, at the end of every wave)

**Revise in place. Never append a correction.** Five checks, ten minutes, before the PR:

1. **Rows against code** — every row touched must match what is actually in the final diff.
2. **Report body against final state** — read it as a stranger; every section states the end
   position.
3. **Numbers** — gate output, test counts, advisory counts, commit ranges go stale first.
4. **Rows live in the wave that owns them.**
5. **Forward instructions** — this wave's Part 6 entry, and constraints written onto later rows,
   reflect what was actually decided.

# Part 4d — Independent review (required, before Part 4b)

Review the wave's full diff **as unreviewed code from a stranger**, against CLAUDE.md and the ADRs —
not by re-checking the list that produced it. Verify every ticked row against the diff (all call
sites, not the one the report named). File what it finds: fix in-wave if the wave introduced it,
otherwise a row in the wave that owns it. This pass found shipped defects in every frontend wave it
ran on; it is a phase, not an owner favour.

# Part 5 — Session protocol

**One wave = one branch = one PR = one fresh session.** Never merge across wave boundaries.

**Context budget.** Each session gets: this ledger, plus the specific `§` sections named in the
wave's rows. Never a whole report, never two.

**Commit granularity and resume.** Commit code per row or small row-group, updating this
(untracked) ledger at the same moment — tick the row when its commit lands, mark it `[~]` when work
starts. If the session dies, the next one reconciles the on-disk ledger against
`git diff main...` and continues from the first unticked row — `/audit:status` does this. Never
batch a whole wave into one uncommitted diff.

**This file is local-only** (`docs/audit/` is gitignored — the repo is public and unfixed findings
must not publish). Snapshot it to `docs/audit/.snapshots/<date>-<time>.md` before any bulk edit, so
a botched edit has a last-good version to diff against; and write every wave's PR body to stand
alone, because a reviewer on GitHub cannot see this file or the wave reports.

**Front-load the owner's decisions.** Before writing code, inventory every row needing a human —
user-visible changes, contrast/colour, anything reopening a ratified decision, rows that name the
owner — and ask them as ONE batch with measured options and recommendations. Ask more rather than
less; a question is cheaper than a reverted wave.

**Close-out, identical every wave:** gate → exit-gate clauses → independent review (4d) → wave
report (4b) → consistency sweep (4c) → commit and push → print the PR title (`Scope: what changed`)
and PR body in one copy-paste block. `gh` is not installed; the owner creates and merges the PR.
